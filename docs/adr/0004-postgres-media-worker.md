# ADR 0004 — PostgreSQL queue for media and document workers

## السياق

فك ترميز الصور واستخراج وثيقة الطبقات عمل ثقيل وغير مناسب لدورة طلب API.
كما يجب ألا يؤدي تشغيل أكثر من Worker إلى معالجة المهمة نفسها مرتين.

## الخيارات

1. تنفيذ متزامن داخل API فقط: بسيط، لكنه يربط زمن الطلب بالمعالجة ولا يتوسع.
2. Redis/BullMQ: مناسب للصفوف الكبيرة، لكنه يضيف مصدر حقيقة ثانٍ قبل الحاجة.
3. صف PostgreSQL باستخدام `FOR UPDATE SKIP LOCKED`: يعتمد على قاعدة البيانات
   الموجودة، ويمنع الاستحواذ المكرر بمعاملة واضحة.

## القرار

نستخدم PostgreSQL كصف أولي لمهام الصور والوثائق:

- ينشئ API سجل `processing_jobs` بحالة `queued`.
- يستحوذ `worker-media` على أقدم مهمة صورة باستخدام
  `FOR UPDATE SKIP LOCKED`.
- يستحوذ `worker-document` على أقدم مهمة `book` بالطريقة نفسها، ويظل
  parser معزولًا عن ميزانية موارد الصور.
- يقرأ المصدر من S3-compatible storage.
- يفك Sharp ترميز الصورة تحت حد 100 مليون بكسل.
- يحفظ `LayerDocument` ثم ينقل المهمة إلى `ready`.
- تبقى المعالجة inline متاحة للاختبارات والتطوير الخفيف فقط، ويُلزم الإنتاج
  وضع `PROCESSING_EXECUTION_MODE=worker`.

## النتائج

- يمكن زيادة عدد عمليات Worker أو `PROCESSING_CONCURRENCY` دون ازدواج
  الاستحواذ.
- PostgreSQL مناسب للحجم الحالي، لكن queue lag وعمليات retry/DLQ يجب إضافتها
  قبل أحمال كبيرة.
- عامل PDF مستقل لأن عزل parser وميزانية موارده تختلف عن الصور. استخراج
  النص المضمّن منفذ؛ OCR يبقى مرحلة مستقلة ويُطلب صراحةً عند الحاجة.

## الرجوع

يمكن إيقاف Worker وإعادة `PROCESSING_EXECUTION_MODE=inline` في بيئة غير
إنتاجية. لا يتطلب الرجوع حذف الجداول، وتبقى المهام المنتظرة قابلة للاستئناف.
