> التدقيق محدثتان في `remaining-production-plan-2026-07-30.md`.

تاريخ التدقيق: 2026-07-28  
حالة الواجهة: الصقل البصري والاستجابة ورحلات المتصفح الأساسية مكتملة ومتحققة.  
نطاق هذه الوثيقة: الأعمال التشغيلية والهندسية المتبقية خارج إعادة التصميم.

## ملخص القرار

لا توجد علامات `TODO` أو `FIXME` أو `HACK` تشير إلى وظيفة واجهة متروكة، كما أن مسارات المنتج الأساسية تعمل في اختبارات المتصفح. ومع ذلك، لا ينبغي إعلان المنظومة جاهزة للإنتاج الكامل قبل إغلاق بنود P0 وP1 التالية، لأنها تتعلق بأمن النقل، وإمكانية إصدار الحاويات واسترجاعها، وسلامة الترحيلات، والتعافي، والمراقبة، واتساع الاختبارات.

## P0 — بوابة الإطلاق

### 1. فرض TLS على تبعيات الإنتاج

النطاق:

- رفض PostgreSQL غير المشفر في الإنتاج ما لم تتضمن الوصلة سياسة SSL المعتمدة.
- رفض `redis://` في الإنتاج وقبول الاتصال المشفر فقط.
- فرض `requireTLS` للبريد عند استخدام STARTTLS، أو اشتراط TLS الضمني.
- تحديث `.env.production.example` ووثائق النشر لتطابق التنفيذ.

اختبارات القبول:

- تفشل اختبارات إعداد الإنتاج مع PostgreSQL أو Redis أو SMTP غير المشفر.
- تنجح البدائل المشفرة المعتمدة.
- لا تسجل الاختبارات أي أسرار أو سلاسل اتصال كاملة.

### 2. إنشاء مسار إصدار بصور حاويات غير قابلة للتبديل

النطاق:

- بناء الصور مرة واحدة داخل Workflow إصدار.
- فحص الصور ثم رفعها إلى Registry صريح بعلامة SHA.
- حفظ digest لكل صورة واستخدامه في النشر والتراجع.
- منع Runbook من الاعتماد على صور محلية أو علامات قابلة لإعادة الكتابة.

اختبارات القبول:

- يستطيع مضيف نظيف سحب الصور بالـdigest وتشغيل المنظومة.
- تنجح فحوص الصحة وSmoke بعد النشر.
- ينجح الرجوع إلى digest الإصدار السابق دون إعادة بناء.

## P1 — سلامة البيانات والتشغيل

### 3. تحويل الترحيلات إلى Expand / Migrate / Contract

النطاق:

- استبدال إعادة تسمية الأعمدة المباشرة بخطوات إضافة متوافقة.
- القراءة والكتابة المزدوجة مؤقتًا ثم Backfill.
- تأجيل حذف العمود القديم إلى إصدار لاحق.
- إضافة SHA-256 للترحيلات المنفذة وقفل PostgreSQL advisory lock.
- رفض أرقام الترحيل المكررة وتعديل الترحيلات السابقة.

اختبارات القبول:

- يعمل الإصداران N وN+1 على المخطط الموسع نفسه.
- ينجح Rollback إلى N بعد نشر N+1.
- يفشل تغيير ترحيل منفذ أو تشغيل مترحلَين متنافسَين بصورة غير آمنة.

### 4. توسيع E2E ليطابق طوبولوجيا الإنتاج

النطاق:

- تشغيل PostgreSQL وRedis وMinIO وMailpit والخدمات والعمال المبنية.
- اختبار التسجيل والدخول والحد من المحاولات بين أكثر من نسخة API.
- اختبار بريد استعادة كلمة المرور من Mailpit.
- اختبار رفع حقيقي ومعالجة وإعادة تشغيل وتصدير وتنزيل.
- اختبار Stripe في Test Mode مع Webhook موقع وIdempotency.

اختبارات القبول:

- تنجح الرحلة الكاملة بعد إعادة تشغيل API والعمال.
- يثبت Redis الحظر بين النسخ.
- تصل رسالة الاستعادة إلى Mailpit.
- لا يكرر Webhook عملية مالية عند إعادة الإرسال.

### 5. تصميم النسخ الاحتياطي والاستعادة وفق RPO/RTO

النطاق:

- تنسيق PostgreSQL PITR مع إصدارات/نسخ Object Storage.
- تفعيل Versioning أو النسخ المتكرر للأصول غير القابلة لإعادة الإنشاء.
- توثيق استعادة مفاتيح التشفير والمالك وجدول الاختبارات.
- إنشاء Runbook استعادة معزول.

اختبارات القبول:

- استعادة قاعدة البيانات والحاوية إلى لحظة محددة.
- فتح مصدر مستعاد وإعادة توليد طبقاته وتصديره.
- تحقيق RPO ≤ 15 دقيقة وRTO ≤ 4 ساعات في تمرين موثق.

### 6. إضافة مراقبة صحة العمال والطوابير

النطاق:

- Queue depth وoldest age وjob duration histograms.
- retries وlease loss وfailed jobs وdependency status.
- heartbeat لكل عامل وHealth probe مستقل.
- حدود CPU/RAM وتنبيهات قابلة للتشغيل.

اختبارات القبول:

- تولد مهمة عالقة تنبيه queue age.
- يولد عامل متوقف حالة unhealthy دون انتظار خروج العملية.
- يمكن اشتقاق p95 من Histogram وليس من مجموع الأزمنة فقط.

### 7. رفع جودة Supply Chain والتغطية

النطاق:

- تثبيت صور الأساس وGitHub Actions بالـdigest/SHA.
- تشغيل واجهة Nginx كمستخدم غير root مع إسقاط capabilities.
- Image scan وSBOM وprovenance وتوقيع digests وsecret scanning.
- إضافة test/coverage scripts لكل Runtime workspace.
- توسيع تغطية الويب لتشمل AppShell والمصادقة والإدارة والمشاريع والتصدير.

اختبارات القبول:

- يفشل CI عند سر مزروع أو ثغرة حرجة في الصورة.
- يثبت فحص Runtime أن العملية غير root ومقيدة الصلاحيات.
- يظهر كل Runtime entrypoint في تقرير التغطية.

## P2 — تخفيض الدين الهندسي

### 8. تثبيت بيئة التطوير

- إعلان Node `>=22.12.0` بدل `>=22`.
- الحفاظ على `.node-version` ومطابقة CI لها.
- تحميل `.env` بطريقة موحدة في أوامر التطوير والترحيل والعمال.
- نجاح تشغيل Durable stack من Checkout نظيف دون Export يدوي للمتغيرات.

### 9. حماية أمر التنظيف

- منع `clean` من حذف مجلد عام تحت `apps/web/src`.
- نقل البيانات المولدة خارج `src` أو حذف ملفات مولدة محددة بالاسم فقط.
- رفض حذف أي مسار متتبع في Git.

اختبار القبول:

- يبقى ملف متتبع تجريبي داخل `apps/web/src/data` بعد `npm run clean`.
- تزال مخرجات البناء المعلنة فقط.

### 10. إنهاء توحيد CSS تدريجيًا

- نقل القواعد من ملفات التصحيح المتراكمة إلى `tokens/base/primitives/shells/features`.
- اعتماد `@layer` بترتيب موثق.
- إزالة `legacy-workspace.css` و`evaluation-polish.css` بعد نقل قواعدهما واختبارها.
- الإبقاء على النصوص التقنية الثانوية فقط في نطاق 11–12px، ورفع النصوص العادية إلى 14px.

اختبارات القبول:

- لا يتغير أي Golden screenshot معتمد.
- لا توجد قواعد حرجة تعتمد على ترتيب استيراد غير موثق.
- لا يوجد نص عادي أصغر من 12px أو هدف لمس أساسي أصغر من 44px.

## ترتيب التنفيذ المقترح

1. TLS ومسار الصور غير القابلة للتبديل.
2. Expand/Contract وسلامة سجل الترحيلات.
3. طوبولوجيا E2E الكاملة.
4. النسخ الاحتياطي والاستعادة والمراقبة.
5. Supply Chain والتغطية.
6. تثبيت التطوير والتنظيف وإزالة دين CSS.

لا تنتقل المنظومة إلى اعتماد إنتاجي نهائي قبل إغلاق البندين P0 وإجراء تمرين الاستعادة واختبار النشر/التراجع بالـdigest.
