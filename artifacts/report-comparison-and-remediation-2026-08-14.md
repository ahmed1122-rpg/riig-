# مقارنة التقرير الإرشادي بالحالة الفعلية وخطة الإغلاق — MotionPrep Studio

**تاريخ المراجعة:** 14 أغسطس 2026
**نسخة الحزمة:** `0.1.8`
**أساس Git المحلي قبل تغييرات هذه الجولة:** `9575c61d8d082a210e64f87af80da40fde3e5c1d` على `main`
**نطاق المراجعة:** التقرير المرفق، شجرة المصدر المحلية، الاختبارات والبوابات المحلية، والحالة العامة الظاهرة لمستودع GitHub.

## 1. الحكم التنفيذي

التقرير صالح كدليل إرشادي، لكن لا يصح تطبيق كل بنوده بوصفها عيوبًا حالية؛ بعض ملاحظات تجربة الطبقات تصف حالة أقدم من الكود الموجود في مساحة العمل. الحكم المصحح هو:

- **الكود محليًا:** متقدم وقابل لإعداد مرشح إصدار بعد تثبيت التغييرات في commit واحد وتشغيل البوابة الكاملة على ذلك الـSHA.
- **الإنتاج العام:** **No-Go**؛ السبب ليس عيب P0 محليًا، بل غياب أدلة الإصدار الخارجية المرتبطة بنفس SHA وdigests: صور `v0.1.8` الموقعة، staging مُدار، restore موقّع، وحمل تمثيلي.
- **ميزات يجب أن تظل مغلقة:** Character Rig وOCR الإقليمي وbilling الحي حتى تنجح بواباتها المستقلة.
- **حد PDF:** ما زال 30 MiB، كما طلب مالك المشروع؛ لم يُرفع إلى 70 MiB.

لا تُعد بوابات التشغيل الخارجية ناجحة لمجرد نجاح Compose أو الاختبارات المحلية.

## 3. الإصلاحات المنفذة استنادًا إلى التقرير

### 3.1 صدق المعاينة

عُدّل صف الطبقة في `LayerDockPanels.tsx` بحيث:

- يعرض `87% · جزء صورة` فقط عندما تكون `confidence=87` موجودة فعليًا.
- يعرض `جزء صورة · الثقة غير متاحة` عند غياب القياس.
- لا يختلق قيمة `94%` أو أي قيمة بديلة.

أضيف اختبارا regression للحالتين.

### 3.2 تفسير رفض الدمج قبل الإرسال

أصبح `useWorkspaceToolController.ts` يحول نتيجة `@motionprep/layer-domain` إلى رسالة عربية محددة قبل فتح dialog أو إرسال mutation. ومن أمثلة ذلك:

- اختلاف مجلد الصفحة: «يجب أن تكون الطبقات داخل المجلد نفسه قبل الدمج.»
- اختلاف الصفحة: «يجب أن تكون طبقات النص في الصفحة نفسها قبل الدمج.»
- اختلاف اتجاه النص أو المحاذاة: يطلب توحيد الخاصية المحددة.
- طبقة مقفلة/ثابتة أو بلا محتوى/حدود: يشرح المانع مباشرة.

أضيف اختبار يثبت رفض دمج طبقتين من مجلدين مختلفين وعدم فتح عملية PDF.

## 4. ما أصبح مكتملًا ولا ينبغي إعادة بنائه

1. تسمية الصفحات كمجلدات `+page_NNN` وربط الخلفية والنصوص بها.
2. فصل عداد الصفحة الحالية عن الإجمالي.
3. حماية المجموعات البنيوية من التحديد والتعديل والتصدير بوصفها محتوى.
4. بحث PDF عبر الصفحات مع فتح المجلد المطابق.
5. ألوان ثابتة حسب ID لا تتغير مع reorder.
6. Sticky headers وbreadcrumb وتسميات RTL/ARIA.
7. قوائم صور virtualized على سطح المكتب والهاتف.
8. أوامر جماعية خادمية مع عدد التحديد على الهاتف وسطح المكتب.
9. coordinator مع flush وإلغاء AbortSignal للعمليات الرئيسية.
10. رفع disk-staged streamed بحد 30 MiB بدل تجميع Buffer كامل في الذاكرة.

إعادة تنفيذ هذه البنود ستزيد المخاطر ولا تضيف قيمة. التطوير التالي يجب أن يبني فوق العقود الحالية.

## 5. الفجوات الحقيقية المتبقية

### P1 — بوابات إصدار خارجية

1. إنشاء commit مرشح نظيف وتشغيل `npm run quality` وE2E على SHA نفسه.
2. إنشاء tag `v0.1.8` بعد نجاح hosted CI فقط.
3. بناء runtime/web images مرة واحدة، إنتاج SBOM/provenance، توقيع Cosign، ثم نشر الـdigests نفسها إلى staging دون rebuild.
4. staging مُدار يثبت PostgreSQL TLS وRedis وS3 المشفر/versioned وSMTP الحقيقي، وفحوص ready للـAPI ولكل worker instance.
5. restore drill موقّع يثبت RPO ≤15 دقيقة وRTO ≤4 ساعات على نفس digests.
6. representative load + fault injection + rollback على staging نفسه.

**معيار GO:** لا يكفي نجاح أحد البنود منفردًا؛ يجب أن يجتمع SHA وtag وdigests وتقارير staging/restore/load/rollback في حزمة evidence واحدة.

### P2 — تجربة الطبقات

1. **Virtualization شجرة PDF كاملة:** تحويل قائمة مجلدات الصفحات إلى virtualizer يدعم ارتفاعات متغيرة، مع إبقاء المجلد الحالي ومخرجات البحث قابلة للوصول. لا تُنفذ بتخفيض DOM عشوائي؛ يجب حفظ focus وARIA والتنقل المحروس.
2. **صف عرض مشترك:** مشاركة presentation model وحساب العنوان/الوصف/الحالة بين Desktop وMobile، مع بقاء تفاعل الهاتف في action drawer مناسب للمساحة.
3. **أوامر هيكلية جديدة عند الحاجة:** `create-group` و`ungroup` و`reparent-layers` و`rename-page-folder` كأوامر خادمية ذرية مع `baseRevision`، تحقق graph، audit event، وundo/redo. لا يضاف أي تعديل شجرة محلي فقط.
4. **معاينة أفضل:** skeleton صادق، حالة «لا توجد معاينة»، وأبعاد/نوع/حجم الأصل من بيانات الخادم فقط. ممنوع استخدام نسب أو labels تخمينية.
5. **اختبار متصفحات:** إضافة Firefox وWebKit إلى بوابة UI أو توثيق دعم Chromium/Edge فقط؛ E2E الحالي لا يثبت Safari/Firefox.

### P2 — صيانة الملفات الكبيرة

المدقق نجح: 472 ملفًا، صفر ملفات أكبر من 550، وصفر clone blocks؛ لكنه أصدر 29 إنذارًا بين 450 و550. الأولوية ليست رفع الحد مرة أخرى، بل استخراج حدود متماسكة من الملفات الأقرب للسقف:

- `processing-routes.ts` (546)
- `postgres-processing-repository.ts` (534)
- `Workspace.tsx` (531)
- `ExportReview.tsx` (528)
- `LayerDock.tsx` (528)
- `postgres-export-repository.ts` (527)
- `auth-service.ts` (525)
- `processing-service.ts` (523)

قاعدة الاستخراج: ملف command/router أو query adapter حقيقي، لا wrapper يمرر المعاملات فقط. كل استخراج يجب أن يحافظ على architecture وmaintainability وtests دون تغيير سلوكي مختلط.

### P3 — التبعيات

- جمّد upgrades الرئيسية أثناء إغلاق 0.1.8.
- أنشئ فرعًا مستقلًا لكل ترقية رئيسية مع migration notes وtypecheck/test/build/E2E/bundle/security.
- ابدأ بتغييرات CI Actions الأقل أثرًا بعد مراجعة breaking changes، ثم Zod 4، واترك TypeScript 7 لآخر موجة مستقلة.
- لا ترفع bundle أو coverage baselines لتسهيل الدمج.

## 6. خطة التنفيذ النهائية

### المرحلة 0 — تثبيت المرشح المحلي

- إنهاء التغييرات الحالية ومراجعة diff كاملة.
- تشغيل quality مرتين دون تغييرات بين التشغيلين.
- تشغيل 12 سيناريو E2E وعينة PDF 250/100,000 ورفع 30 MiB.
- التأكد من عدم وجود أسرار أو artifacts مؤقتة أو harness محلي داخل commit.

**القبول:** worktree نظيف بعد commit واحد أو سلسلة صغيرة مفهومة، وكل بوابة مرتبطة بـSHA المرشح.

### المرحلة 1 — CI والإصدار الموقّع

- دفع فرع `codex/...` وفتح PR.
- مراجعة hosted CI وCodeQL/Trivy/secret scan.
- دمج المرشح ثم إنشاء `v0.1.8` من SHA المدمج فقط.
- توقيع الصور والتحقق من provenance وSBOM.

**القبول:** tag وruntime digest وweb digest جميعها تشير إلى المصدر نفسه.

### المرحلة 2 — staging والاستعادة والحمل

- نشر digests الموقعة دون rebuild.
- migrations، smoke، ready per instance، اختبار queue lease/retry.
- backup/restore وعينة تحقق كائنات وإصدارات.
- حمل PDF تمثيلي وحقن أعطال ثم rollback.

**القبول:** تقارير موقعة تحقق أهداف RPO/RTO والموارد وSLO، ولا يبقى queue أو object orphan بعد الاختبار.

### المرحلة 3 — تحسين طبقات PDF بعد تجميد 0.1.8

- RFC صغير لـvariable-height PDF virtualization وعقد focus/ARIA.
- تنفيذ presentation model مشترك للهاتف/سطح المكتب.
- إضافة الأوامر الهيكلية فقط إذا أصبحت حاجة مستخدم مؤكدة، مع server CAS وundo/audit.
- Browser matrix وvisual regression عند 375/768/1024/1440.

## 7. أدلة التحقق الحالية

- اختبارات الإصلاح المركزة: 3 ملفات، 7 اختبارات، كلها ناجحة.
- حزمة اختبارات الويب بعد الإصلاح: 67 ملفًا، 235/235 اختبارًا ناجحًا.
- Web typecheck وESLint للملفات المتأثرة و`git diff --check`: ناجحة.
- Production web build: ناجح؛ 163 module جرى تحويلها، ونُقلت source maps الخاصة خارج `dist`.
- ميزانية الحزمة: ناجحة؛ JavaScript ‏179.6 KiB من حد 180، وCSS ‏45.1 KiB من حد 50. الهامش ضيق ويجب عدم رفع baseline أو إضافة eager dependency قبل تحليل chunk.
- `verify:maintainability`: ناجح؛ 472 ملفًا، صفر oversized، صفر exact clones، و29 early warnings.
- الدفعة المحلية السابقة على مساحة العمل نفسها: اختبارات الجذر الكاملة، lint، stylelint، deadcode، architecture، contracts، security و12/12 E2E كانت ناجحة قبل إصلاحي النص والرسالة. أُعيدت الآن بوابات الويب المتأثرة والبناء والحزمة؛ وتبقى إعادة `npm run quality` كاملة بعد تجميد diff مباشرة قبل commit المرشح.
- أحدث tag ظاهر محليًا وعلى GitHub هو `v0.1.7`; لا يظهر `v0.1.8` في صفحة Tags بتاريخ الفحص.
- GitHub العام يعرض 10 Pull Requests مفتوحة، وSecurity and quality = 0. هذه بيانات آنية عامة وليست بديلًا عن evidence محمي.

## 8. القرار النهائي

التقرير معتمد كخريطة مخاطر، لا كنسخة حرفية من الحالة الحالية. أُغلقت الملاحظتان البرمجيتان المؤكدتان اللتان بقيتا منه: صدق نسبة الثقة وتفسير رفض الدمج. بقية عناصر طبقات كثيرة كانت منجزة بالفعل، والمتبقي الحقيقي في المنتج هو full PDF virtualization، توحيد presentation، والأوامر الهيكلية الاختيارية.

**قرار النشر يبقى No-Go** حتى إنشاء `v0.1.8` موقّع وتشغيل staging/restore/load/rollback على نفس SHA والـdigests. بعد تحقق ذلك فقط يصبح canary داخلي قرارًا مسؤولًا.
