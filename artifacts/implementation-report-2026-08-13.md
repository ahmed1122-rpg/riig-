# تقرير تنفيذ التحسينات — 13 أغسطس 2026

## النتيجة التنفيذية

اكتملت الحزمة المحلية ذات الأولوية من خطة المراجعة، والسقف النهائي لرفع الصور وملفات PDF هو **30 MiB (31,457,280 بايت)**. يُطبّق الحد في العقود المشتركة، وتهيئة API، والتحقق من طلب الرفع، وخدمة الرفع، وواجهة المستخدم، وNginx، واختبارات النشر.

اعتمدت سياسة الملفات التالية:

- حفظ المصدر الأصلي كما رفعه المستخدم وعدم ضغطه أو استبداله داخل المتصفح.
- إنشاء المعاينات والملفات المشتقة بصورة منفصلة، بما يحافظ على إمكانية إعادة المعالجة والتدقيق.
- استخدام الضغط غير الفاقد في التصدير حيث تدعمه الصيغة؛ يتضمن المسار الحالي ضغط PNG التكيفي، وTIFF باستخدام LZW، وأرشفة المخرجات بصورة غير حاجبة.
- رفض الملف مبكرًا برسالة دقيقة بحسب نوعه: PDF أو صورة، بدل حد واحد غامض لكليهما.

## ما نُفّذ

### الرفع والحدود

- فصل حد PDF عن حد الصور في العقود والقدرات التي يعلنها الخادم.
- قبول الصور وملفات PDF حتى 30 MiB ورفض ما يتجاوز ذلك، مع اختبارات للحد الفاصل.
- تطبيق السقف نفسه على نوعي المصدر، مع الإبقاء على إمكان خفض حد الصور تشغيليًا عند الحاجة.
- ضبط `client_max_body_size` في Nginx على `30m` وتحديث أمثلة متغيرات البيئة والوثائق ودليل التشغيل.
- عرض الحد الصحيح داخل مربع رفع PDF في سطح المكتب والهاتف.

### سلامة المحرر والبيانات

- منع مناطق PDF ذات القيم غير المحدودة أو الأبعاد الصفرية أو التي تتجاوز الصفحة، في الواجهة والخادم.
- توحيد ترتيب القراءة، وجعل مناطق الاستثناء بلا ترتيب رقمي، وإعادة ترقيم بقية المناطق بصورة متصلة.
- استخدام معرفات UUID للعناصر الجديدة لمنع تصادم المعرفات.
- إضافة تحذير موحد عند محاولة مغادرة محرر يحوي مسودة محلية غير محفوظة، ويشمل الرجوع وتغيير المصدر والوضع والصفحة وإغلاق التبويب.
- فصل منطق هندسة الصورة وPDF إلى وحدات قابلة للاختبار، وخفض الملفات المتضخمة تحت حد قابلية الصيانة.
- استخراج تشخيص فشل المعالجة في وحدة مستقلة مع حجب رسائل المزود الخام والبيانات غير المرتبطة.

### الطبقات والصفحات وتجربة الاستخدام

- عرض طبقات صفحة PDF الحالية فقط، مع توافق رجعي آمن للبيانات القديمة.
- إصلاح عنوان الصفحة في قائمة الطبقات بدل القيمة الثابتة.
- تحديد عدد صفوف الطبقات المرسومة أوليًا على الهاتف إلى 64 مع زر إظهار المزيد.
- جعل الأدوات غير المتاحة قابلة لاكتشاف قارئ الشاشة ولوحة المفاتيح، باستخدام `aria-disabled` وسبب تعطيل ظاهر، مع منع التنفيذ فعليًا.
- تحسين دلالات مناطق المحرر وإزالة أدوار وتركيزات زائفة كانت تربك تقنيات الوصول.

### الأداء وبيئة العمل

- تقسيم حزمة الواجهة إلى أجزاء React والأيقونات والمكوّنات المشتركة.
- خفض JavaScript المضغوط إلى **167.4 KiB** ضمن ميزانية المشروع البالغة 168 KiB، مع بقاء هامش صغير يستلزم المراقبة.
- إضافة `npm run dev:durable` لتشغيل PostgreSQL وRedis وMinIO وMailpit، وتطبيق migrations، ثم تشغيل API والواجهة والعمال.
- إعلان الخادم عن نمط التخزين `ephemeral` أو `durable` وعرض تحذير واضح في الواجهة عند العمل بتخزين مؤقت.
- إضافة Request ID إلى خطأ تحميل القدرات لسهولة التتبع التشغيلي.

## قرار الجاهزية

**الحالة المحلية: ناجحة وقابلة للمراجعة والدمج.**

**الإنتاج العام: مشروط، وليس Go نهائيًا بعد.** يحتفظ Fastify بجسم طلب الرفع في الذاكرة قبل تسليمه للتخزين. خفض السقف إلى 30 MiB يقلل الخطر، لكن يجب إثبات السلوك تحت حمل متزامن في بيئة مماثلة للإنتاج.

### بوابات الإنتاج المتبقية

1. نشر نفس commit وصور الحاويات على staging ثم اختبار ملفات عند الحد 30 MiB وعند تجاوزه مباشرة عبر Nginx وAPI والتخزين الكائني.
2. تنفيذ حمل متزامن واقعي وقياس RSS، وزمن الرفع، ومعدلات 413/429/5xx، والمهلات، وحجم مساحة الملفات المؤقتة، وأثر الرفع في طوابير العمال.
3. تحديد حد التزامن ومعدل الرفع وفق النتائج؛ وإذا اقترب استهلاك الذاكرة من الحدود، نقل الرفع الكبير إلى multipart/resumable مباشر نحو التخزين الكائني باستخدام روابط موقعة.
4. تنفيذ اختبارات الاستعادة والنسخ الاحتياطي والفشل والرجوع للإصدار السابق، مع حفظ الأدلة التشغيلية.
5. استكمال أدلة OCR الحالية على مجموعة holdout مختومة قبل تفعيل Region OCR في الإنتاج؛ التحقق المحلي يتركها معطلة عمدًا عند غياب الدليل.
6. التحقق من المزودات الخارجية، وسياسات الاحتفاظ والحذف، ومسح البرمجيات الخبيثة للملفات، ومراقبة Sentry/المقاييس على staging.
