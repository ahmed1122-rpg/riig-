# تقرير التنفيذ والتدقيق النهائي — MotionPrep

**التاريخ:** 2026-07-28  
**نطاق التدقيق:** الرفع، المعالجة، التصدير، الاستجابة، المزامنة، الكاش،
الذاكرة، الأمان، الموثوقية، التشغيل، والوظائف المخطط لها.

## النتيجة التنفيذية

اكتمل البناء البرمجي الحالي ونجحت بوابات الجودة المحلية. لا توجد أداة
معطلة معروضة للمستخدم في نسخة الإنتاج: الأدوات الجاهزة فقط هي التي تظهر،
أما الوظائف التي لا تملك عقد خادم واختبارات كاملة فتبقى مصنفة
`planned` ومخفية في الإنتاج.

هذا لا يساوي تصريح إطلاق إنتاجي بعد. الإطلاق مشروط بتشغيل CI المستضاف،
اختبار PostgreSQL/MinIO الفعلي، فحص تخزين S3 في staging، وتجربة
الاستعادة من النسخ الاحتياطية.

## ما نُفّذ

### 1. الاستجابة وطبقة HTTP

- مهلة صريحة لكل طلب، وتمييز واضح بين انقطاع الشبكة وانتهاء المهلة.
- تحليل آمن للاستجابات الفارغة وHTML وJSON غير الصالح أو غير المكتمل.
- أخطاء typed تحفظ `status`, `code`, `requestId`, و`retryable`.
- إعادة المحاولة للعمليات الآمنة فقط، أو للطلب المتغير الذي يحمل مفتاح
  idempotency.
- backoff قابل للإلغاء لمتابعة مهام المعالجة والتصدير.
- رسائل صحيحة لحالة rate limit بدل إظهار خطأ كلمة مرور مضلل.

### 2. الرفع والمعالجة والتصدير

- رفع بايتات فعلي مع progress، مهلة، إلغاء، وفحص Magic Bytes والحجم.
- ترميز آمن لمعرفات المسارات في العميل.
- إصدارات مصدر منفصلة، SHA-256، وأصول Raster مشتقة ومتحقق منها.
- عقود متجددة للعمال، استرداد بعد توقف العامل، ومحاولات محدودة بتأخير
  تصاعدي.
- إنشاء التصدير بعد تفريغ autosave، مع ربطه صراحة بمراجعة الوثيقة
  وإصدار المصدر.
- منع العامل من تصدير مراجعة أقدم من المطلوبة.
- عامل تصدير فعلي يحفظ الناتج في التخزين ثم ينهي المهمة ذريًا.
- سجل استخدام دائم للفوترة بدل الاعتماد على عدادات ذاكرة العملية.

### 3. المزامنة والكاش والذاكرة

- طابور autosave متسلسل لا يسمح لرد قديم بالكتابة فوق حالة أحدث.
- حالة حفظ مرئية مع retry، وفشل التصدير مغلقًا إذا لم تُحفظ المراجعة.
- تحميل معاينات Raster بتزامن محدود وإعادة استخدام cache بدل إطلاق كل
  الطلبات دفعة واحدة.
- حدود Sharp للذاكرة والكاش والتزامن.
- حدود CPU وRAM وملفات مؤقتة لكل خدمة في Compose.
- نافذة محدودة لطبقات PDF الكبيرة لحماية DOM والذاكرة.

### 4. الأمان والموثوقية

- التحقق من TLS لـPostgreSQL وRedis وS3 وSMTP في الإنتاج.
- فرض same-origin بين الويب وAPI في الإنتاج.
- حماية metrics داخل الشبكة الخاصة مع دعم bearer token.
- تشغيل الصور كمستخدم غير root، filesystem للقراءة فقط، إسقاط جميع
  capabilities، و`no-new-privileges`.
- ترحيلات بــadvisory lock وchecksum تمنع تشغيل ملف تغيّر بعد تطبيقه.
- تغييرات الإدارة وسجل التدقيق داخل transaction واحدة.
- CodeQL وDependabot ومسح Trivy لصورتي التشغيل والويب.
- صور إصدار بعلامة `sha-<full commit SHA>` مع SBOM وprovenance وdigests.

### 5. التشغيل والصيانة

- heartbeats للعمال وحالتها في metrics وAPI ولوحة الإدارة.
- مهمة retention idempotent تحذف bytes أولًا ثم تعلم الصف في قاعدة
  البيانات؛ فشل التخزين يبقي العنصر قابلًا لإعادة المحاولة ويعيد exit code
  غير صفري.
- تنظيف جلسات الرفع والتصدير، الجلسات الأمنية، MFA، reset tokens،
  idempotency، heartbeats، وسجلات المهام وفق مدد صريحة.
- احتفاظ افتراضي 400 يوم لسجل التدقيق والاستخدام و90 يومًا للمهام
  النهائية، مع اشتراط اعتماد قانوني لأي تقصير.
- runbooks للإصدار والتراجع، استرداد المهام، الرفع/التصدير، والاستعادة
  المنسقة لقاعدة البيانات والتخزين.

### 6. الواجهة وتجربة الهاتف

- أخطاء جلب إصدارات المصدر تظهر للمستخدم مع retry ولا تتحول إلى قائمة
  فارغة مضللة.
- إصلاح بقاء scrim درج الهاتف بعد التسجيل؛ جميع مداخل المصادقة تغلق
  الدرج، والنجاح يغلقه دفاعيًا مرة أخرى.
- اختبار نفس رحلة الطبقات على الهاتف وفق التحكم الحقيقي المتاح في شاشة
  المراجعة.
- إضافة favicon لإزالة طلب 404 غير الضروري.

## الوظائف غير المكتملة عمدًا

هذه ليست أزرارًا معطلة في الإنتاج؛ هي مسارات منتج مؤجلة ومخفية:

| الوظيفة | النقص الفعلي المطلوب قبل الإتاحة |
|---|---|
| تحسين حواف الصورة | عامل يولد Raster مشتقًا جديدًا مع عقد حفظ واختبارات جودة |
| دمج طبقات الصورة | دمج غير هدّام مع مراجعة قابلة للاستعادة |
| OCR لمنطقة PDF | إرسال قصاصة الصفحة الأصلية للعامل وعقد OCR إقليمي |
| فصل وحدة نص PDF | تحرير geometry والعلاقات وترتيب القراءة |
| دمج وحدات نص PDF | دمج النص والهندسة وإعادة فهرسة ترتيب القراءة |
| استعادة إصدار مصدر سابق | سجل الإصدارات والفتح موجودان؛ تغيير الإصدار الحالي/rollback الآمن غير موجود |

كما تبقى دورة حياة المشروع الكاملة (حذف/استعادة)، مواصفة OpenAPI،
واختبارات الحمل والذاكرة على ملفات 30 MiB أعمالًا تشغيلية مطلوبة قبل
توسيع الاستخدام، وليست أعطالًا في المسار الحالي.

## بوابات خارجية لم تُنفذ في هذه الآلة

1. **CI المستضاف:** الملفات موجودة، لكن المستودع بلا commit baseline وكل
   الملفات ما تزال untracked؛ لذلك لا يوجد run أخضر أو branch protection.
2. **PostgreSQL 17 + MinIO:** اختبار التكامل مكتوب ويشمل الترحيلات،
   التخزين، retention، استرداد العقود، وحلقة عامل التصدير. Docker daemon
   المحلي لم يستجب، لذلك لم يُشغّل هنا.
3. **S3 في staging:** يجب تشغيل `npm run verify:object-storage` بهوية
   التشغيل والحاوية الحقيقية.
4. **بيئة الإنتاج:** يلزم إثبات TLS الفعلي وSMTP وRedis وStripe webhooks
   وأسرار المنصة، لا مجرد تحقق الإعدادات.
5. **التعافي من الكوارث:** يلزم تمرين استعادة من نسخة PostgreSQL ونسخة
   object storage متوافقتين وقياس RPO/RTO.
6. **Adobe:** الفحص البنيوي ناجح؛ الفتح في إصداري Photoshop وAfter
   Effects المستهدفين يحتاج الترخيص والبيئة الفعلية.
7. **OCR تسويقي:** عينة smoke ناجحة، لكن يلزم corpus كتب عربية ممثل
   ومرخص قبل نشر ادعاءات دقة.

## خطة التنفيذ المتبقية

### P0 — قبل أي إطلاق إنتاجي

1. إنشاء baseline Git، دفع الفرع، وتفعيل حماية `main`.
   **القبول:** CI أخضر لكل jobs: quality، containers، Trivy،
   durable-integration، browser-e2e، وCodeQL.
2. نشر صورتي runtime/web بالـSHA نفسه في staging وتشغيل migrations.
   **القبول:** health live/ready، رحلة رفع وتصدير، وعدم وجود migration
   checksum drift.
3. تشغيل فحص object storage بهوية workload الفعلية.
   **القبول:** write/read/checksum/encryption/delete/post-delete كلها ناجحة.
4. جدولة maintenance كل ساعة وإثبات إعادة محاولة حذف متعثر.
   **القبول:** exit غير صفري عند فشل التخزين ثم نجاح الدورة التالية بلا
   فقد metadata.
5. تنفيذ تمرين restore.
   **القبول:** manifest واحد يربط نقطة PostgreSQL بنسخة object storage،
   وRPO ≤ 15 دقيقة وRTO ≤ 4 ساعات أو أهداف أعمال بديلة معتمدة.

### P1 — أول دورة تقوية بعد staging

1. اختبار حمل وذاكرة بمزيج PNG/PDF حتى 30 MiB وقياس p95 وذروة RSS.
2. نشر OpenAPI من العقود والتحقق منه في CI.
3. إضافة حذف/استعادة مشروع بسياسة retention وتدقيق إداري.
4. تشغيل Golden داخل Adobe الفعلي وتوثيق الإصدارين.
5. توسيع corpus OCR وقياس CER حسب نوع الخط وجودة المسح.

### P2 — وظائف المنتج المؤجلة

الترتيب الموصى به: استعادة إصدار المصدر، OCR المنطقة، فصل/دمج وحدات
النص، تحسين الحواف، ثم الدمج غير الهدّام. لا تنتقل أي وظيفة إلى `ready`
إلا بعد اكتمال عقد API، migration عند الحاجة، worker behavior، autosave،
rollback/disablement، metrics، واختبارات وحدة وتكامل ومتصفح.
